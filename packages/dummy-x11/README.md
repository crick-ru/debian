# dummy-x11

Упаковка **написана с нуля** для этого репозитория: исходников нет и быть не
может — пакет состоит из библиотеки-заглушек, которая генерируется из
списков символов, настоящей `libxcb` из trixie и диагностического скрипта.

## Зачем пакет

Официальный `yandex-browser-stable` из репозитория Яндекса
(`https://repo.yandex.ru/yandex-browser/deb stable main`) — бинарный пакет
без исходников. Пересобрать его без X11 нельзя, а поставить его нельзя:
`Depends` требует `libx11-6`, `libxcb1`, `libxcomposite1`, `libxdamage1`,
`libxext6`, `libxfixes3`, `libxrandr2`.

Этот пакет даёт системе недостающие имена пакетов, кладёт на место настоящих
X11-библиотек заглушки, а вместо `libxcb` — настоящую библиотеку из trixie
(см. «Почему libxcb настоящая»).

## Почему не patchelf, и почему нельзя просто удалить зависимости

Первое, что приходит в голову, — `patchelf --remove-needed`. **Так не
работает**, и причина существенная:

```
$ readelf -d yandex_browser | grep FLAGS
 0x000000000000001e (FLAGS)   BIND_NOW
```

Debian собирает браузер с `-Wl,-z,now`, то есть `BIND_NOW`: динамический
линкер разрешает **все** импорты при старте, а не по первому обращению.
Удаление `NEEDED` приводит не к отложенной ошибке, а к немедленной:

```
$ patchelf --remove-needed libX11.so.6 ... yandex_browser
$ ./yandex_browser --version
symbol lookup error: undefined symbol: XFixesQueryExtension
```

Поэтому пакет кладёт на место настоящих библиотек заглушки **с теми же
именами файлов**: линкер находит библиотеку по имени, все импорты
разрешаются, и программа стартует без X-сервера. Бинарник браузера и все
библиотеки из его поставки остаются нетронутыми — `patchelf` не применяется
вообще.

## Одна библиотека вместо восьми

Все заглушки собраны в **один файл** `dummy-x11.so` (SONAME тоже
`dummy-x11.so`), а имена настоящих библиотек — симлинки на него:

```
libX11.so.6 -> dummy-x11.so    libXfixes.so.3  -> dummy-x11.so
libXext.so.6 -> dummy-x11.so   libXrandr.so.2  -> dummy-x11.so
libXcomposite.so.1 -> dummy-x11.so             libXau.so.6  -> dummy-x11.so
libXdamage.so.1 -> dummy-x11.so                libXdmcp.so.6 -> dummy-x11.so
```

Линкер ищет файл по имени из `NEEDED`, находит симлинк и грузит цель.
Повторно под другим именем glibc тот же файл не грузит — в
`_dl_map_object_from_fd` есть сверка `dev/inode`, поэтому восемь `NEEDED`
дают одну загрузку. Проверено на glibc из trixie бинарником, собранным
против двух разных SONAME, указывающих на один файл.

Объединение безопасно потому, что символы заглушек без версионных тегов и
все возвращают `NULL`: разрешение символов идёт по первому загруженному
объекту, у которого есть весь набор из всех списков.

## Почему libxcb настоящая

Заглушка `libxcb.so.1` не давала браузеру запуститься — экспериментальным
путём установлено, что ему нужна настоящая библиотека. В пакет она взята
без изменений из trixie: `libxcb1_1.17.0-2+b1`, файл
`/usr/lib/x86_64-linux-gnu/libxcb.so.1.1.0` переименован в имя его SONAME
`libxcb.so.1` (`sha256 a1cde2cec9b7b8b38e4cca450c55c63651efb80a2458d76964b56b763043f533`).

Два следствия:

1. **Символы libxcb не входят в объединение.** Иначе заглушки `xcb_*`
   перебили бы настоящие функции (объединение грузится первым), и реальная
   libxcb превратилась бы в фиктивную. Список `symbols-libxcb.so.1.txt`
   поэтому используется только отчётом — для проверки покрытия импортов
   браузера.
2. **Настоящая libxcb ссылается по `NEEDED` на `libXau.so.6` и
   `libXdmcp.so.6`** (аутентификация X11), и без них браузер не загрузится
   даже с настоящей libxcb. Решение: заглушки этих двух библиотек входят в
   `dummy-x11.so` наравне с остальными. Функции аутентификации вызываются
   только при подключении к X-серверу, которого в целевой системе нет.
   Пакет конфликтует с `libxau6`/`libxdmcp6` и провайдит их (как и
   `libxcb1`), поэтому apt снимет настоящие пакеты, а зависимости настоящей
   libxcb закроются нашими заглушками.
   Из-за этого `dh_shlibdeps` отключён в `debian/rules`: иначе сборка
   потребовала бы настоящие `libxau6`/`libxdmcp6` в `Build-Depends` только
   ради метаданных, а внешних зависимостей у пакета нет по замыслу.

## Что лежит в пакете

| Файл | Назначение |
|---|---|
| `/usr/lib/x86_64-linux-gnu/dummy-x11.so` | единая библиотека-заглушка (SONAME `dummy-x11.so`) |
| `…/libX11.so.6`, `…/libXext.so.6` | симлинки → `dummy-x11.so` |
| `…/libXcomposite.so.1`, `…/libXdamage.so.1` | симлинки → `dummy-x11.so` |
| `…/libXfixes.so.3`, `…/libXrandr.so.2` | симлинки → `dummy-x11.so` |
| `…/libXau.so.6`, `…/libXdmcp.so.6` | симлинки → `dummy-x11.so` (нужны настоящей libxcb) |
| `…/libxcb.so.1` | **настоящая** библиотека из trixie, не заглушка |
| `/usr/bin/dummy-x11-report` | диагностический скрипт (см. ниже) |
| `/usr/share/dummy-x11/gen-stubs` | генератор заглушек, для диагностики |
| `/usr/share/dummy-x11/symbols-*.txt` | списки символов (для отчёта) |

### Символы: почему список полный, а не только используемые браузером

Заглушка экспортирует **все** символы настоящей библиотеки, а не только те
43, что зовёт браузер. Это обязательно: транзитивные X11-библиотеки ссылаются
на внутренние символы друг друга. Например `libXrender.so.1` тянет
`_XUnlockMutex_fn` из `libX11.so.6`, и заглушка с урезанным списком её ломает:

```
$ ./yandex_browser --version
symbol lookup error: /usr/lib/.../libXrender.so.1: undefined symbol: _XUnlockMutex_fn
```

Списки получены один раз с настоящих библиотек trixie через
`readelf --dyn-syms` (все определённые динамические символы) и зафиксированы
в репозитории: 2232 имени во всех списках, из них 1556 собираются в
`dummy-x11.so`, а список `libxcb` (676) — только для отчёта. Сборка не
зависит от состава trixie.

Почти все символы — функции; исключения — 58 переменных `libX11`
(например `_XUnlockMutex_fn`, `_Xdebug`), и для них заглушка вида
`void *f(void)` тоже допустима: на переменную ссылается только внутренний
код библиотек X11, а его в целевой системе нет (настоящая libxcb такими
символами не пользуется). Версионных тегов у символов нет.

Возвращаемое значение задано явно — не «как получится». Браузер проверяет
`XOpenDisplay()` на `NULL` и по нему выбирает бэкенд; мусор в регистре
привёл бы к попытке работать через несуществующий X-сервер.

## Диагностический скрипт

Скрипт ничего не меняет в системе: вызов остаётся за пользователем.

```bash
dummy-x11-report            # сводка и недостающие символы (по умолчанию)
dummy-x11-report --full     # полный отчёт: сводка + зависимости по файлам
dummy-x11-report --snapshot # записать текущее состояние эталоном
dummy-x11-report --compare  # сравнить с эталоном (код 1 = есть новые символы)
```

Отчёт показывает:

1. версию браузера;
2. состояние заглушек: путь, число символов, каких файлов не хватает;
   у настоящей `libxcb` это помечено отдельно;
3. символы: сколько X11-вызовов импортирует браузер, сколько покрыто
   заглушками, каких не хватает;
4. с `--full` — зависимости **по каждому файлу** поставки, с разделением:
   - `X11 (dummy-x11)` — закрывается этим пакетом (заглушки и настоящая libxcb);
   - `наши из репозитория` — приходят из пакетов нашего репозитория, где X11
     уже вырезан (например `libxkbcommon.so.0`);
   - `прочие (не X11)` — ни прямо, ни косвенно с X11 не связаны, их можно
     ставить без оговорок.

## Что делать, если браузер не запускается

Браузер обновляется сам и заменяет свои файлы целиком, а заглушки живут в
отдельном пакете: новая версия может потребовать X11-вызовов, которых в
списках нет.

1. Запустить `dummy-x11-report` — он назовёт недостающие символы.
2. Дописать их в соответствующий `debian/stubs/symbols-<SONAME>.txt`.
3. Пересобрать `dummy-x11` (ревизия Debian поднимается, если список уже был
   опубликован).

Состав пакета меняется от версии к версии — это единственная причина, по
которой списки символов приходится пополнять. Режимы `--snapshot` и
`--compare` как раз для того, чтобы заметить обновление сразу: `--snapshot`
записывает текущее состояние эталоном, `--compare` затем показывает, что
изменилось, и возвращает код 1, если появились новые X11-символы.

## Побочные эффекты

- **Доступность (скринридеры) не работает.** Заглушки покрывают только
  клиентские библиотеки X11; `at-spi2-core` собирается отдельно и без X11
  (см. его README).
- Пакет конфликтует с настоящими X11-библиотеками (и с `libxau6`/
  `libxdmcp6`): в системе, где X11 используется по-настоящему, ставить его
  нельзя, `apt` снимет эти пакеты.
